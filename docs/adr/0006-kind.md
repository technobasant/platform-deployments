# 6. A three-node kind cluster

Status: accepted · 2026-10

## Context

The tests need more than one node: a drain has to move pods somewhere, topology
spread has to have somewhere to spread, and a PodDisruptionBudget only means
something when evictions compete with capacity. The options were kind, k3d and
VMs.

## Decision

* kind: one control plane and two workers, each a container, running upstream
  Kubernetes (kubeadm, containerd, kindnet with NetworkPolicy support).
* etcd's data directory is on the control-plane node's tmpfs. On disk, etcd request
  timeouts during bootstrap cost the controller manager its leader lease.
* The same `kind/cluster.yaml` runs in CI.

## Why not k3d

k3d starts faster and is lighter, but it runs k3s: SQLite or embedded etcd, a
bundled ingress and load balancer, and Flannel. kind runs the same components as a
kubeadm cluster, which is what the measurements should describe.

## Consequences

* All nodes share one host, so node-to-node latency is local and network failure
  modes are out of reach. The figures are for scheduling, rollout and disruption
  behaviour, not for networking.
* etcd on tmpfs does not survive a node restart. The cluster is disposable.
